# LLM match / KoboldCPP

Нативная игра против локальной языковой модели. Модель **сама выбирает ход**;
список допустимых ходов ей не отправляется. Легальность проверяет `engine`, а
шаблоны, роли, подсчёт контекста и Kobold API обслуживает `prompt-core` из
`../../ai-tg-bot/crates/prompt-core` (путь относительно этого крейта).

## Запуск в игре

Обычные шахматы 8×8 описаны в разделе **Classic Chess / SAN** ниже. Это отдельный
вариант, не существующий representation-профиль с именем `classic`.

1. Запусти KoboldCPP с загруженной моделью и доступным API.
2. Проверь [`.env`](.env): адрес KoboldCPP, context/instruct/reasoning для своей
   модели, sampler preset и четыре пути `LLM_*_TEMPLATE` этапов.
3. Запусти `cargo run -p bevy-front`, выбери **LLM**, вариант, цвет и адрес
   KoboldCPP. Нажми начало игры. Ползунка сложности у LLM нет.
4. Внизу показывается ожидание, повтор после недопустимого ответа или ошибка.
   После ошибки нажми розовую кнопку **Retry** под сообщением, чтобы повторить
   запрос той же позиции.

Это **desktop-интеграция**, не WASM: HTTP-клиент `prompt-core` работает через
Tokio. В браузерной сборке кнопка LLM не добавляется. Для неё нужен отдельный
browser transport либо серверный прокси; HTTPS-сайт также не может просто
обращаться к локальному HTTP-Kobold без учёта mixed content/CORS.

Без графики:

```sh
cargo run -p llm-match -- --variant TerachessII --black
cargo run -p llm-match -- --variant Gothic --url http://aistation:5001
```

Ходы вводятся в UCI, `quit` завершает матч. CLI позволяет проверить модель,
не запуская рендерер.

## Настройки без пересборки

`.env`, профили и правила читаются при создании матча, не встраиваются в бинарник
рабочего пути генерации. Настройки фиксируются до следующей партии, чтобы
эксперимент не менялся посреди игры.
`LLM_MATCH_ENV=/absolute/path/.env` задаёт другой файл; переменные окружения
имеют приоритет над значениями файла. Относительные пути шаблонов и пресета
считаются от директории `.env`. При переносе бинарника перенеси эти файлы и
задай `LLM_MATCH_ENV` (иначе используется путь исходников при сборке).

| Переменная | Назначение |
| --- | --- |
| `LLM_KOBOLD_URL` | Начальный адрес поля меню; поле переопределяет его для матча |
| `LLM_CONTEXT_TEMPLATE` | Шаблон общего контекста |
| `LLM_INSTRUCT_TEMPLATE` | Формат ролей/разделителей именно загруженной модели |
| `LLM_REASONING_TEMPLATE` | Prefix/suffix/separator reasoning-блока |
| `LLM_ANALYST_TEMPLATE` | `templates/pipeline/analyst.json` |
| `LLM_PROPOSER_TEMPLATE` | `templates/pipeline/proposer.json` |
| `LLM_VERIFIER_TEMPLATE` | `templates/pipeline/verifier.json` |
| `LLM_SELECTOR_TEMPLATE` | `templates/pipeline/selector.json` |
| `LLM_PRESET` | Sampler preset в формате prompt-core/SillyTavern |
| `LLM_REQUEST_TIMEOUT_SECONDS` | Таймаут каждого HTTP-запроса |
| `LLM_MAX_ATTEMPTS` | Максимум раундов proposer → verifier → selector, сейчас 8 |
| `LLM_STAGE_MAX_ATTEMPTS` | Максимум запросов одного этапа/кандидата, включая тихие повторы; по умолчанию 3 |
| `LLM_PROFILES_FILE` | TOML-файл экспериментов, по умолчанию `representation-profiles.toml` |
| `LLM_PROFILE` | Имя профиля, переопределяющее `active_profile` из TOML |
| `LLM_RULES_DIR` | Каталог отдельных файлов правил, по умолчанию `rules` |

Context/instruct/reasoning должны соответствовать загруженной модели.
`genamt` в пресете ограничивает суммарный ответ, включая reasoning. Текущие
значения бюджета и таймаута смотри в файлах настроек; они не зашиты в код.
После опционального reasoning аналитик возвращает свободный текст; остальные этапы — JSON-объект.
Вложенные поля ходов используют формат профиля: SAN, семантический текст,
числовой текст, UCI или numeric JSON.
Поддерживаются настроенный полный prefix с channel-токенами и его XML opener
`<thinking>`. Нешахматный общий `strip_from_output` из prompt-core здесь не
используется: шахматному адаптеру нужно отличать незавершённый блок от ответа.

## Четыре этапа

Single-pass runtime заменён для всех вариантов. Classic получает FEN + ASCII;
fairy-варианты получают состояние и геометрию согласно выбранному профилю.
Числовые профили не получают FEN или дополнительные буквенные координаты.

1. **Position Analyst** получает позицию, последний ход, отклонённые ходы и
разрешённую профилем историю. Не выбирает ход. Возвращает анализ в любом удобном
   формате: текст, списки, Markdown или JSON. Нет обязательных полей и лимитов
   на число фактов/длину отдельного факта. Proposer получает финальный текст
   без JSON-переупаковки и без скрытого reasoning.
2. **Candidate Proposer** получает ту же позицию, последний ход, историю,
   компактный анализ и исключённые попытки. Ответ:
   `{"candidates":[{"id":"c1","move":"Nf6","from":"g8","to":"f6","rationale":"..."} , ...]}`.
   Нужно 3–5 кандидатов; id уникальны, до 32 символов. rationale — необязательная
   строка со свободным объяснением, без ограничения в 320 символов.
   Дубликаты ходов и ранее исключённые попытки отбрасываются приложением.
   После фильтрации допустимо меньше трёх кандидатов.
3. **Independent Verifier** вызывается отдельно для каждого оставшегося кандидата,
   последовательно. Получает только позицию, правила и `id/move/from/to`.
   Не получает историю, анализ, rationale и другие кандидаты. Ответ:
   `{"candidate_id":"c1","verdict":"ACCEPT","reason":"..."}` либо `REJECT`.
   reason — необязательная строка без ограничения в 320 символов. Проверяет геометрию, пути, занятость, специальные
   правила, безопасность короля и немедленные тактические опровержения.
4. **Selector** получает только текущую позицию и принятых кандидатов с заметками
   verifier. Возвращает `{"candidate_id":"c1","final_move":"Nf6"}`.
   Не может изменить ход или выбрать исключённого кандидата.
   Даже один выживший кандидат проходит этот этап.

Это четыре роли, обычно **6–8 генераций на ход** без повторов.
Каждый запрос строится заново; весь hidden reasoning остаётся внутри своего
запроса. Повторное использование HTTP-клиента не означает общую историю LLM.

Во всех схемах запрещены лишние поля. Для Classic `move/final_move` — строка
канонического SAN. В остальных профилях — строка соответствующего формата либо
JSON-объект numeric_json, например
`{"from":[5,2],"to":[5,4],"promotion":null}`.
`from/to` кандидата — строки клеток для Classic/pieces_ascii и массивы `[x,y]`
для numeric/numeric_ascii. Координаты абсолютные, с единицы.
Это только проверка представления: до selector движок не фильтрует легальность.

Каждый файл этапа поддерживает `content`, `user_prompt`, `post_history`.
Дополнительные директивы:
- `{{analysis}}` — свободный финальный текст аналитика, только у proposer;
- `{{candidate}}` — один кандидат без rationale, только у verifier;
- `{{accepted-candidates}}` — массив с `verifier_note`, только у selector;
- `{{excluded-moves}}` — попытки, исключённые в текущем вызове, только у proposer;
- Булевы флаги для `{{#if ...}}`: `classic`, `numeric-coordinates`,
  `output-uci`, `output-numeric-json`, `output-semantic`, `output-numeric`,
  `history-enabled`. Они позволяют выбирать инструкции прямо в JSON-файле.

Недоступные этапу данные отсутствуют в окружении шаблона. Обычные
`fen/ascii/board-state/side-to-move` доступны согласно профилю.
`last-move/classic-san-history/wrong-move` доступны только аналитику и proposer.
Весь системный текст задаётся JSON-файлом этапа: Rust ничего к нему не дописывает.
Поставляемые JSON-шаблоны явно включают FEN/ASCII или board-state/chess-rules
и содержат инструкции форматов в условных блоках. Если удалить директиву,
соответствующие данные не появятся автоматически. Прежние `authoritative-state`,
`stage-rules`, `move-format` и текстовые `*-instructions` в окружении этапов
больше не предоставляются: инструкции перенесены в JSON. Парсеры ответов по-прежнему
проверяют JSON-схемы proposer/verifier/selector; редактирование промпта не меняет их протокол.
Аналитик не имеет схемы ответа. Общий защитный лимит финального ответа этапа —
32 КиБ; незавершённый reasoning и пустой ответ по-прежнему вызывают тихий повтор.
Списки легальных ходов, оценки движка и вычисленные подсказки не вставляются.
`--print-prompt` показывает реальный начальный запрос аналитика.

## Reasoning и повторы

Незакрытый reasoning, reasoning без результата, неправильный JSON или нарушение
схемы вызывают тихий повтор того же этапа с тем же входом. Аналогично повторяются
timeout/connect/408/429/5xx с задержкой 100, 200, 400, 800, затем 1600 мс.
Ошибки конфигурации/контекста и прочие HTTP-ошибки завершают запрос.
Ни одна из этих ситуаций не создаёт `Event::Rejected` и не меняет доску/истории.

Аналитик выполняется один раз на вызов генерации. Когда все кандидаты отклонены
или отфильтрованы, начинается новый раунд proposer. Отказы verifier сохраняются
только как временные исключения текущего вызова. Их причины не пересылаются proposer.

Выбранный ход проверяется движком на копии матча, включая соответствие
заявленным `from/to`. При успехе результат атомарно переносится в матч.
При отказе сохраняется только выбранный ход в `wrong_moves`, отправляется
`Event::Rejected`, затем повторяется proposer → verifier → selector с прежним
анализом. Причина отказа движка и альтернативы модели не передаются.

По исчерпании любого лимита доступен ручной Retry. Он начинает новый анализ,
сохраняя окончательные отказы, но не временные отказы verifier.
Логи показывают этап, номер попытки и раунда без полного reasoning.
Принятые SAN/UCI-истории и состояние фронтенда изменяются только после успеха.

## Правила и директивы

[`rules/`](rules/) содержит **отдельный загружаемый файл для каждого из десяти
вариантов**: `capablanca.txt`, `gothic.txt`, `embassy.txt`, `schoolbook.txt`,
`bird.txt`, `carrera.txt`, `grand.txt`, `shako.txt`, `pemba.txt`, `terachess-ii.txt`.
Их можно редактировать без сборки, изменения вступят в силу в новой партии.
Размер доски, маршруты рокировки и разрешённые
суффиксы обычного промоушена берутся из `VariantRules`. Описаны нестандартные
фигуры, Grand-воскрешение и Terachess II. Легенда содержит одну фигуру на строку
и запрещает угадывать её по букве или привычной стартовой клетке. Названия,
символы и базовые описания принадлежат `engine`: `PieceKind::display_name`,
`movement_description`, `VariantRules::piece_symbol`. Геометрия leaper-фигур
строится из тех же массивов смещений, что и генерация ходов: жираф —
`(2,3)/(3,2)`, не `(1,4)`. Промоушен, рокировка, rapid pawns и прыжок короля
остаются правилами варианта. Для Gothic явно указан исходный ряд a-j.

Файлы правил поддерживают `{{board-header}}`, `{{piece-legend}}`,
`{{castling-rules}}`, `{{pawn-rules}}`, `{{promotion-rules}}`,
`{{initial-back-rank}}` и условие `{{#if numeric}}...{{/if}}`.
Эти вставки автоматически адаптируются к профилю. Для эксперимента можно
заменять их собственным буквальным текстом. Это изменяет только инструкцию
модели, **не правила движка**; за корректность вручную изменённых правил
отвечает автор эксперимента. Все десять файлов должны существовать.

Новые директивы реализованы через штатный `PromptData.custom`, без изменений
соседнего проекта:

- `{{chess-rules}}` — выбранные правила в начальном system prompt;
- `{{side-to-move}}` — `White` или `Black` из текущей позиции движка. Доступна
  во всех вариантах и профилях, в `content`, `user_prompt` и `post_history`;
- `{{board-state}}` — явный side to move, сохранённые права рокировки,
  en-passant target, initial king jump для Terachess II, CURRENT PIECES и ASCII;
- `{{wrong-move}}` — JSON-список отклонённых final moves текущего хода и указание,
  что позиция не изменилась и повторять их нельзя.
- Инструкции представления и формата ответа задаются условными блоками
  в JSON этапов, а не Rust-директивами `*-instructions`.

В прежнем single-pass [`templates/sysprompt/Chess.json`](templates/sysprompt/Chess.json)
использовались такие вставки (файл сохранён для справки, runtime его не читает):

```text
{{board-state}}
{{#if wrong-move}}
{{wrong-move}}
{{/if}}
```

Это поле `SystemPromptTemplate.post_history`: prompt-core вставляет его
**после истории, перед следующим assistant turn**. Значения директив не
вычисляются как новые шаблоны. Отказы остаются данными, не сообщениями роли
assistant/user. Не удаляй эти директивы из пользовательского system template.

В модельном контексте **нет FEN**. Список и ASCII читаются непосредственно
из `Position`/`Board`; группы фигур отсортированы по английскому имени,
координаты — по файлу, затем числовому рангу. Символы в inventory/легенде
верхнего регистра, цвет задаёт раздел White/Black; в ASCII чёрные — lowercase.
`Castling: yes` означает сохранённое право, а не разрешение рокироваться сквозь
фигуры или шах. Для отсутствующих прав/целей выводятся `none`/`no`.

## Гарантии и ограничения

- Истории содержат только принятые ходы. `Match::uci_history()` хранит
  canonical UCI для синхронизации с `ChessMatch.move_history`.
  `Match::history()` содержит PromptMessage: человек — `User`, модель —
  `Assistant`, но текст семантический: `White Pawn e2-e4`,
  `White Bishop h8xe5`, `White Pawn a7-a8=Queen`.
  `x` ставится только при взятии (включая en passant); рокировка, en passant
  и initial king jump явно помечаются. Тип фигуры берётся **до применения** хода.
  `Match::numeric_history()` хранит параллельное числовое описание. Выбор
  формата и усечение истории влияют только на запрос, не на синхронизацию.
  Позиции, сетевые ошибки и отвергнутые ответы в обе истории не записываются.
- После reasoning аналитик принимает любой непустой текст; остальные этапы — целый JSON-объект своей схемы.
- JSON также можно обернуть в один Markdown-блок ` ```json ` или ` ``` `.
  Закрывающая строка ` ``` ` обязательна. Текст вне блока, несколько блоков
  и некорректный JSON не принимаются. Это поддерживается для всех трёх
  структурированных этапов и numeric JSON ходов; проверки схемы и легальности
  не меняются.
  Поле хода проверяется в формате профиля: SAN для Classic, формат истории
  или canonical UCI для соответствующих fairy-профилей. Регистр и неверные
  ходы автоматически не исправляются; промоушен проверяется движком.
- Нелегальный ответ не меняет доску. Следующий запрос содержит ту же позицию
  и те же принятые ходы, но обновлённый временный список отказов. При ошибке
  сети/исчерпании попыток список сохраняется для ручного повтора. При легальном
  ходе очищается. Новый матч начинает новую историю.
- История не ограничена числом ходов. `prompt-core::build_with_budget` сначала
  пробует весь контекст и только при реальном переполнении убирает старейшие
  сообщения из конкретного запроса. Правила, текущая позиция и последнее
  сообщение сохраняются. Постоянные истории не изменяются. Если обязательные
  блоки сами не помещаются, возвращается ошибка. Размеры проверяются токенизатором модели.
- Сеть работает вне потока рендера. Модель начинает после окончания анимации.
  Открытие меню/новая игра отменяют клиентское ожидание; запоздалые ответы не
  применяются. Это не глобальная команда abort серверу: Kobold может закончить
  уже начатую генерацию, но её результат больше не используется.
- Сила LLM не гарантируется: проверка легальности не является тактической
  подсказкой и не заменяет её ход Stockfish-ходом.

## Эксперименты с представлением позиции

Профили проверяют, провоцируют ли традиционная нотация и история стандартно-
шахматные предположения у LLM. Списков легальных ходов, оценок и подсказок нет.

Настройки: [representation-profiles.toml](representation-profiles.toml).
Каждый эксперимент имеет **ровно два варианта: полная история или отсутствие
истории**. Они отличаются только `history_mode`, а не форматом ответа.

| С историей | Без истории | Состояние | История и ответ |
| --- | --- | --- | --- |
| `classic` (по умолчанию) | `classic-no-history` | pieces_ascii | semantic |
| `numeric` | `numeric-no-history` | numeric | numeric |
| `numeric-ascii` | `numeric-ascii-no-history` | numeric_ascii | numeric |
| `hybrid` | `hybrid-no-history` | numeric_ascii | semantic |
| `uci` | `uci-no-history` | pieces_ascii | uci |
| `numeric-json` | `numeric-json-no-history` | numeric | numeric_json |

```toml
active_profile = "numeric"

[profiles.numeric]
state_format = "numeric"
history_mode = "full"
history_format = "numeric"
output_format = "numeric"
```

- `state_format`: `pieces_ascii` — имена/символы и ASCII; `numeric` —
  абсолютные координаты; `numeric_ascii` — числовой список плюс ASCII.
- `history_mode`: только `full` или `none`. **`last_n` и `history_count`
  удалены**; старые настройки с ними отклоняются.
- `history_format` и `output_format`: `semantic`, `numeric`, `uci`,
  `numeric_json`. При включённой истории обязаны совпадать.
- `full` отправляет все принятые полуходы в хронологическом порядке, без
  искусственного лимита; лишь реальное переполнение включает штатный сдвиг
  контекста prompt-core. `none` не отправляет ни одного сообщения истории.
- Полная каноническая история UCI сохраняется независимо от профиля.
  Роли: человек — User, модель — Assistant.

Выбор без пересборки:

```sh
cargo run -p bevy-front -- --llm-profile numeric
cargo run -p llm-match -- --variant Gothic --llm-profile numeric-json
LLM_PROFILE=classic-no-history cargo run -p bevy-front
```

Приоритет: **CLI > окружение LLM_PROFILE > .env LLM_PROFILE > active_profile**.
Имя профиля видно в меню, форматы — в логе начала партии.
`RUST_LOG=llm_match=debug` показывает final answer, внутренний UCI и число
старых сообщений, удалённых из запроса при сдвиге контекста.
Отказы передаются модели только в её формате, без внутреннего преобразования.
Профиль фиксируется на партию.

Миграция: `classic-last-move` → `classic`;
`numeric-last-move`/`numeric-short-history` → `numeric`;
`numeric-ascii-last-move` → `numeric-ascii`.
Прежний JSON-эксперимент без истории теперь называется
`numeric-json-no-history`; `numeric-no-history` использует числовой текст,
как его парный вариант с историей.

### Форматы ходов

```text
semantic: White Pawn e2-e4
numeric:  White Pawn: (5,2) -> (5,4)
uci:      e2e4
```

JSON (одинаковая схема в истории и в ответе):

```json
{"from":[5,2],"to":[5,4],"promotion":null}
```

Все три JSON-поля обязательны; дополнительные/повторяющиеся ключи, нецелые
или выходящие за доску координаты запрещены. Промоушен — точное имя
(`"Queen"`, не `"queen"`). Например
`{"from":[2,8],"to":[3,6],"promotion":null}` декодируется в `b8c6`;
это только преобразование, не гарантия легальности и не исправление хода.

В semantic/numeric взятие обозначается `x`, промоушен — `=Queen` /
` = Queen`. Спецходы требуют аннотации ` (en-passant)`,
` (initial king jump)` либо ` (castling; Rook a1-d1)` /
` (castling; Rook (1,1) -> (4,1))`.
В UCI/JSON спецходы выражаются координатами без этих аннотаций.
Semantic/numeric парсер сравнивает всю строку с описанием движка из
**предходовой** позиции: цвет, фигура, взятие и спецходы не исправляются.
Никаких SAN, извлечения подстрок или нормализации регистра.
Человек в CLI по-прежнему вводит UCI.

### Координаты и состояние

`x=file+1`, `y=rank`: a1=(1,1), j8=(10,8), для Terachess II p16=(16,16).
При ходе Black оси не зеркалируются. В модельном numeric-промпте нет буквенной
системы координат и таблицы соответствий: x растёт слева направо, y — от края
White к краю Black, если смотреть со стороны White. Названия фигур остаются английскими.
NumericAscii намеренно добавляет обычную буквенную ASCII-доску.

Состояние содержит очередь, фигуры, права рокировки/en passant, initial king
jump Terachess, счётчики и число повторений текущей позиции; Grand также
начальные количества фигур для восстановления. Нет FEN.
Геометрические описания находятся рядом с правилами движка; leaper-смещения
общие с генератором ходов, Giraffe=(2,3)/(3,2).
Редактирование загружаемых файлов правил изменяет промпт, не правила движка.

### Посмотреть промпт без модели

```sh
cargo run -p llm-match -- --variant Gothic --llm-profile numeric-no-history --print-prompt
cargo run -p llm-match -- --variant Gothic --llm-profile numeric --moves 'e2e4 e7e5' --print-prompt
cargo run -p llm-match -- --variant TerachessII --llm-profile numeric-json --print-prompt
```

`--moves` задаёт историю каноническими UCI; HTTP-запросов нет.

### Начальная позиция для тестирования

```sh
cargo run -p llm-match -- --variant Classic \
  --fen 'rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR b KQkq - 0 17' \
  --moves 'e7e5' --print-prompt
```

`--fen '...'` (или `--fen=...`) разбирается движком по правилам выбранного
`--variant`, включая extended FEN нестандартных вариантов. Без опции используется
обычная расстановка. Очередь, права и счётчики берутся из FEN; история до этой
позиции не восстанавливается, в том числе прежние повторения. `--moves` задаёт
принятые ходы **после** указанной позиции. Без `--print-prompt` начинается игра
из этой позиции; `--black` по-прежнему выбирает сторону человека.
Примеры представления: [Gothic без истории](examples/gothic-numeric-no-history.txt),
[Gothic с историей](examples/gothic-numeric-history.txt),
[Terachess](examples/terachess-numeric-no-history.txt).

Архитектура: `profile.rs` — конфигурация; `representation.rs` — состояние,
история и JSON/UCI; `move_text.rs` — грамматика текстовых ходов;
`rules.rs` — подстановка в редактируемые файлы правил.

## Classic Chess / SAN

В меню вариантов добавлен **Classic Chess**: обычная расстановка 8×8,
рокировка e1–g1/c1 (и аналогично у чёрных), en passant, промоушен только в
Queen/Rook/Bishop/Knight. Local, AI (Fairy-Stockfish `chess`) и LLM используют
один движок правил. Для Multiplayer добавлено отдельное wire-имя `classic`;
нужно обновить backend вместе с фронтом, миграции таблиц не требуется.
Общий механизм завершения партий движка сохранён: мат/пат, повторения и
правило 50 ходов. Это не реализация турнирных процедур заявления ничьей FIDE.

LLM-конфигурация классики **отдельная**: [classic-profiles.toml](classic-profiles.toml),
шаблоны в [templates/classic/](templates/classic/). Старые
`representation-profiles.toml`, `LLM_PROFILE`, `--llm-profile` и profile
`classic` не переименованы и не меняют смысл. Для `Variant::Classic` они не
выбирают представление; вместо них используются:

| Настройка | Значение |
| --- | --- |
| `LLM_CLASSIC_PROFILES_FILE` | Путь от `.env`, по умолчанию `classic-profiles.toml` |
| `LLM_CLASSIC_PROFILE` | `with-history` или `no-history` |
| `LLM_ANALYST_TEMPLATE` и остальные три пути этапов | Общие для обоих режимов истории и всех вариантов |
| `--llm-classic-profile` | CLI-переопределение, приоритет над env и `.env` |
| `active_profile` в classic TOML | По умолчанию `no-history` |

Адрес Kobold, instruct/context/reasoning и sampler preset остаются общими.
Четыре шаблона этапов загружаются независимо от наличия истории.
`LLM_SYSTEM_TEMPLATE`, `LLM_CLASSIC_SYSTEM_TEMPLATE` и старое поле
`system_template` classic TOML больше не выбирают runtime-промпт.
Старые пользовательские файлы не удалены; перенеси нужные инструкции в
соответствующие новые файлы, соблюдая назначение этапа и его JSON-схему.
`include_history` управляет только принятой историей аналитика и proposer.
Verifier и selector всегда работают без истории.

Fairy-конфигурация не требует
наличия classic-файлов, а классика не загружает fairy-профили и файлы правил.

```sh
cargo run -p bevy-front -- --llm-classic-profile with-history
# Затем выбрать Classic Chess и режим LLM в меню.
cargo run -p llm-match -- --variant Classic --llm-classic-profile no-history
cargo run -p llm-match -- --variant Classic --moves 'e2e4 e7e5 g1f3 b8c6' --print-prompt
```

Директивы этой отдельной ветки:

- `{{ascii}}` — ASCII текущего `Position`;
- `{{fen}}` — FEN того же `Position`, включая очередь, права и счётчики;
- `{{side-to-move}}` — `White` или `Black`, в зависимости от текущей очереди хода;
- `{{last-move}}` — последний принятый SAN-ход, даже в `no-history`; до первого хода — пустая строка;
- `{{classic-san-history}}` — принятые ходы в PGN-movetext, например
  `1. e4 e5 2. Nf3 Nc6`. Это текст ходов без PGN-заголовков/комментариев;
  при старте с хода чёрных сохраняется номер: `23... a1=Q+`.

`with-history` передаёт все принятые ходы отдельными сообщениями: ход человека —
`User`, ход модели — `Assistant`, независимо от цвета. Содержимое каждого сообщения —
только канонический SAN (`e4`, `e5`, `Nf3`), точно как требуемый ответ модели.
Лимита количества ходов нет; при переполнении контекстом управляет prompt-core.
`no-history` не передаёт сообщений истории (директива также возвращает пустую строку).
SAN формируется движком из позиции **до** каждого принятого хода; внутренний UCI
для frontend синхронизации сохраняется отдельно. Отказы и reasoning в историю не входят.
`{{classic-san-history}}` остаётся необязательной PGN-вставкой для пользовательских
шаблонов; стандартные шаблоны её не используют, чтобы не дублировать сообщения.

Поле JSON `user_prompt` необязательно. Оно рендерится тем же `prompt-core`
с теми же директивами и `if`-блоками, затем добавляется отдельным последним
сообщением User, перед системным `post_history`. В постоянную историю оно
не записывается; учитывается в бюджете контекста и не обрезается вместе с историей.
Например:

```json
{
  "name": "Classic experiment",
  "content": "Play chess. End your answer with a canonical SAN move.",
  "user_prompt": "{{#if last-move}}Last move: {{last-move}}. {{/if}}Choose your move.",
  "post_history": "AUTHORITATIVE POSITION\n{{fen}}\n{{ascii}}\n{{wrong-move}}"
}
```

В обоих режимах selector возвращает JSON, например
`{"candidate_id":"c1","final_move":"Nf3"}`. Поле должно совпадать с кандидатом,
принятым verifier. Свободный текст и `FINAL_MOVE: Nf3` вместо JSON не принимаются.
В постоянную историю попадает только принятый движком SAN, без JSON-оболочки.
Старый парсер конечного хода остаётся внутренней вспомогательной функцией,
но ответы этапов через него не извлекаются из произвольного текста.
Разрешение неоднозначности учитывает только легальные исходные фигуры;
лишняя/недостающая disambiguation, неверный `+/#`, `0-0` и UCI не
исправляются. CLI-ввод человека и `--moves` остаются UCI для совместимости.

Тихие reasoning/transport retries сохранены. Только настоящий final SAN
может попасть в минимальный список отказов; нелегальные попытки не меняют
SAN-историю, UCI-историю или позицию. FEN/ASCII в `post_history` authoritative.
Генерируемые легальные ходы/оценки/подсказки модели не передаются. Для Gothic
и Terachess новые SAN-правила, FEN-директивы и classic-шаблоны не включаются.

## Проверки

```sh
cargo test -p llm-match
cargo test -p capablanca-engine -p bevy-front --lib --tests
```

Короткие тесты проверяют роли, неизменность позиции/истории после отказов,
строгий UCI, промоушен, двузначные ряды, все варианты и шаблоны. Подставной
HTTP-Kobold проверяет полное/оборванное reasoning, отсутствие final answer,
тихие повторы с неизменным prompt, ошибки HTTP/таймауты и настоящие отказы.
Проверяются семантические взятия/промоушен/спецходы, синхронизация UCI,
геометрия leaper-фигур, отсутствие FEN и утечек legal moves. Реальная модель
для тестов не нужна.

Тесты профилей дополнительно проверяют все клетки досок 10×8/16×16,
абсолютные координаты для Black, выбор none/full и сдвиг контекста, CLI/env precedence,
строгую JSON-схему, alias-защиту промоушена, точное совпадение semantic/numeric
ответов с историей (включая спецходы), запрет несовместимых настроек и
синхронизацию числового режима с UCI-историей фронтенда.
