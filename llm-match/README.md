# LLM match / KoboldCPP

Нативная игра против локальной языковой модели. Модель **сама выбирает ход**;
список допустимых ходов ей не отправляется. Легальность проверяет `engine`, а
шаблоны, роли, подсчёт контекста и Kobold API обслуживает `prompt-core` из
`../../ai-tg-bot/crates/prompt-core` (путь относительно этого крейта).

## Запуск в игре

1. Запусти KoboldCPP с загруженной моделью и доступным API.
2. Проверь [`.env`](.env): адрес `http://aistation:5001`, context `Plain`,
   instruct `Gemma_4`, reasoning `Artemis_think`, system `Chess_artemis_think`
   и [`presets/Chess.json`](presets/Chess.json).
3. Запусти `cargo run -p bevy-front`, выбери **LLM**, вариант, цвет и адрес
   KoboldCPP. Нажми начало игры. Ползунка сложности у LLM нет.
4. Внизу показывается ожидание, повтор после недопустимого ответа или ошибка.
   После ошибки нажми розовую кнопку **Retry** под сообщением, чтобы повторить
   запрос той же позиции.

Это **desktop-интеграция**, не WASM: HTTP-клиент `prompt-core` работает через
Tokio. В браузерной сборке кнопка LLM не добавляется. Для неё нужен отдельный
browser transport либо серверный прокси; HTTPS-сайт также не может просто
обращаться к локальному HTTP-Kobold без учёта mixed content/CORS.

Без графики:

```sh
cargo run -p llm-match -- --variant TerachessII --black
cargo run -p llm-match -- --variant Gothic --url http://aistation:5001
```

Ходы вводятся в UCI, `quit` завершает матч. CLI позволяет проверить модель,
не запуская рендерер.

## Настройки без пересборки

`.env`, профили и правила читаются при создании матча, не встраиваются в бинарник
рабочего пути генерации. Настройки фиксируются до следующей партии, чтобы
эксперимент не менялся посреди игры.
`LLM_MATCH_ENV=/absolute/path/.env` задаёт другой файл; переменные окружения
имеют приоритет над значениями файла. Относительные пути шаблонов и пресета
считаются от директории `.env`. При переносе бинарника перенеси эти файлы и
задай `LLM_MATCH_ENV` (иначе используется путь исходников при сборке).

| Переменная | Назначение |
| --- | --- |
| `LLM_KOBOLD_URL` | Начальный адрес поля меню; поле переопределяет его для матча |
| `LLM_CONTEXT_TEMPLATE` | Шаблон общего контекста |
| `LLM_INSTRUCT_TEMPLATE` | Формат ролей/разделителей именно загруженной модели |
| `LLM_REASONING_TEMPLATE` | Prefix/suffix/separator reasoning-блока |
| `LLM_SYSTEM_TEMPLATE` | Общая оболочка шахматных правил и `post_history` |
| `LLM_PRESET` | Sampler preset в формате prompt-core/SillyTavern |
| `LLM_REQUEST_TIMEOUT_SECONDS` | Таймаут каждого HTTP-запроса |
| `LLM_MAX_ATTEMPTS` | Общий бюджет попыток хода (включая тихие повторы), по умолчанию 8; далее ручной повтор |
| `LLM_PROFILES_FILE` | TOML-файл экспериментов, по умолчанию `representation-profiles.toml` |
| `LLM_PROFILE` | Имя профиля, переопределяющее `active_profile` из TOML |
| `LLM_RULES_DIR` | Каталог отдельных файлов правил, по умолчанию `rules` |

Context/instruct/reasoning должны соответствовать загруженной модели.
`genamt` в пресете ограничивает суммарный ответ, включая reasoning. Текущие
значения бюджета и таймаута смотри в файлах настроек; они не зашиты в код.
Artemis сначала выдаёт краткий `<thinking>...</thinking>`, затем один ответ
в выбранном формате (семантический, числовой текст, UCI или numeric JSON).
Поддерживаются настроенный полный prefix с channel-токенами и его XML opener
`<thinking>`. Нешахматный общий `strip_from_output` из prompt-core здесь не
используется: шахматному адаптеру нужно отличать незавершённый блок от ответа.

## Reasoning и сетевые повторы

- Незакрытый reasoning или закрытый блок без final answer: вся генерация
  молча отбрасывается. `accept_model` не вызывается, доска, обе истории и
  `wrong_moves` неизменны, `Event::Rejected` не создаётся. Модели не сообщается
  об обрыве, следующий запрос получает тот же контекст.
- Полные ведущие reasoning-блоки удаляются по разделителям. Остаток целиком
  должен иметь синтаксис выбранного формата. Нельзя вырезать ход из прозы, склеивать
  координаты вокруг reasoning, исправлять регистр или использовать SAN.
  Проза/пустота/неправильный формат также повторяются без передачи текста модели.
- Только синтаксически корректный final move передаётся в `accept_answer`.
  Если движок отвергает его, обратная связь минимальна:
  `Rejected moves: ["e7e4"]. Position unchanged. Do not repeat them.`
  Причины нелегальности, альтернативы и reasoning никогда не подмешиваются.
- Timeout/connect/HTTP 408/429/5xx повторяются без model-visible изменений,
  с задержкой 100, 200, 400, 800, затем 1600 мс. Это касается подключения,
  подсчёта токенов и генерации. Ошибки шаблонов/контекста/пресета и остальные
  HTTP-ошибки завершают запрос сразу. После исчерпания бюджета доступен ручной
  повтор; прежние настоящие отклонённые ходы сохраняются.

## Правила и директивы

[`rules/`](rules/) содержит **отдельный загружаемый файл для каждого из десяти
вариантов**: `capablanca.txt`, `gothic.txt`, `embassy.txt`, `schoolbook.txt`,
`bird.txt`, `carrera.txt`, `grand.txt`, `shako.txt`, `pemba.txt`, `terachess-ii.txt`.
Их можно редактировать без сборки, изменения вступят в силу в новой партии.
Размер доски, маршруты рокировки и разрешённые
суффиксы обычного промоушена берутся из `VariantRules`. Описаны нестандартные
фигуры, Grand-воскрешение и Terachess II. Легенда содержит одну фигуру на строку
и запрещает угадывать её по букве или привычной стартовой клетке. Названия,
символы и базовые описания принадлежат `engine`: `PieceKind::display_name`,
`movement_description`, `VariantRules::piece_symbol`. Геометрия leaper-фигур
строится из тех же массивов смещений, что и генерация ходов: жираф —
`(2,3)/(3,2)`, не `(1,4)`. Промоушен, рокировка, rapid pawns и прыжок короля
остаются правилами варианта. Для Gothic явно указан исходный ряд a-j.

Файлы правил поддерживают `{{board-header}}`, `{{piece-legend}}`,
`{{castling-rules}}`, `{{pawn-rules}}`, `{{promotion-rules}}`,
`{{initial-back-rank}}` и условие `{{#if numeric}}...{{/if}}`.
Эти вставки автоматически адаптируются к профилю. Для эксперимента можно
заменять их собственным буквальным текстом. Это изменяет только инструкцию
модели, **не правила движка**; за корректность вручную изменённых правил
отвечает автор эксперимента. Все десять файлов должны существовать.

Новые директивы реализованы через штатный `PromptData.custom`, без изменений
соседнего проекта:

- `{{chess-rules}}` — выбранные правила в начальном system prompt;
- `{{board-state}}` — явный side to move, сохранённые права рокировки,
  en-passant target, initial king jump для Terachess II, CURRENT PIECES и ASCII;
- `{{wrong-move}}` — JSON-список отклонённых final moves текущего хода и указание,
  что позиция не изменилась и повторять их нельзя.
- `{{representation-instructions}}`, `{{history-instructions}}`,
  `{{output-instructions}}` — адаптивные инструкции выбранного профиля.
  Все три обязательны в system template: это предотвращает незаметное
  противоречие старого UCI-шаблона числовому эксперименту.

В [`templates/sysprompt/Chess.json`](templates/sysprompt/Chess.json):

```text
{{board-state}}
{{#if wrong-move}}
{{wrong-move}}
{{/if}}
```

Это поле `SystemPromptTemplate.post_history`: prompt-core вставляет его
**после истории, перед следующим assistant turn**. Значения директив не
вычисляются как новые шаблоны. Отказы остаются данными, не сообщениями роли
assistant/user. Не удаляй эти директивы из пользовательского system template.

В модельном контексте **нет FEN**. Список и ASCII читаются непосредственно
из `Position`/`Board`; группы фигур отсортированы по английскому имени,
координаты — по файлу, затем числовому рангу. Символы в inventory/легенде
верхнего регистра, цвет задаёт раздел White/Black; в ASCII чёрные — lowercase.
`Castling: yes` означает сохранённое право, а не разрешение рокироваться сквозь
фигуры или шах. Для отсутствующих прав/целей выводятся `none`/`no`.

## Гарантии и ограничения

- Истории содержат только принятые ходы. `Match::uci_history()` хранит
  canonical UCI для синхронизации с `ChessMatch.move_history`.
  `Match::history()` содержит PromptMessage: человек — `User`, модель —
  `Assistant`, но текст семантический: `White Pawn e2-e4`,
  `White Bishop h8xe5`, `White Pawn a7-a8=Queen`.
  `x` ставится только при взятии (включая en passant); рокировка, en passant
  и initial king jump явно помечаются. Тип фигуры берётся **до применения** хода.
  `Match::numeric_history()` хранит параллельное числовое описание. Выбор
  формата и усечение истории влияют только на запрос, не на синхронизацию.
  Позиции, сетевые ошибки и отвергнутые ответы в обе истории не записываются.
- Принимается только весь `trim()` final answer после reasoning: один строгий
  JSON-объект выбранной схемы, точная строка формата истории либо canonical UCI:
  `e2e4`, `a7a8q`, `d15g12`. Никаких SAN, markdown, извлечения подстрок или
  исправления регистра. Суффиксы промоушена проверяются движком.
- Нелегальный ответ не меняет доску. Следующий запрос содержит ту же позицию
  и те же принятые ходы, но обновлённый временный список отказов. При ошибке
  сети/исчерпании попыток список сохраняется для ручного повтора. При легальном
  ходе очищается. Новый матч начинает новую историю.
- Если настроенный контекст не помещается, запрос завершается явной ошибкой:
  история **не обрезается автоматически**, иначе эксперимент `full` незаметно
  стал бы другим. Выбери `last_n`/`none` или увеличь контекст. Размер контекста
  и токены берутся из API модели, не оцениваются по числу символов.
- Сеть работает вне потока рендера. Модель начинает после окончания анимации.
  Открытие меню/новая игра отменяют клиентское ожидание; запоздалые ответы не
  применяются. Это не глобальная команда abort серверу: Kobold может закончить
  уже начатую генерацию, но её результат больше не используется.
- Сила LLM не гарантируется: проверка легальности не является тактической
  подсказкой и не заменяет её ход Stockfish-ходом.

## Эксперименты с представлением позиции

Цель профилей — проверить, провоцируют ли традиционная шахматная нотация и
полная история нежелательные стандартно-шахматные предположения у LLM в
fairy chess, прежде всего Gothic и Terachess II. Это не обещание усиления модели.
Списки легальных ходов, оценки, кандидаты, карты атак и подсказки движка
**не передаются ни в одном профиле**.

Настройки: [`representation-profiles.toml`](representation-profiles.toml).
Можно добавлять собственные секции и смешивать представления состояния и
истории. По дополнительному требованию **при включённой истории формат ответа
обязан совпадать с её форматом**. Несовместимое сочетание отклоняется, а не
незаметно исправляется:

```toml
active_profile = "classic"

[profiles.my-experiment]
state_format = "numeric"
history_mode = "last_n"
history_count = 4
history_format = "numeric"
output_format = "numeric"
```

| Поле | Значения |
| --- | --- |
| `state_format` | `pieces_ascii`: символы, имена, координаты a1, ASCII; `numeric`: имена и абсолютные (x,y); `numeric_ascii`: numeric плюс обычная ASCII-доска |
| `history_mode` | `none`: 0 сообщений истории; `full`: все принятые полуходы; `last_n`: последние N в хронологическом порядке |
| `history_count` | Положительное целое, обязательно для `last_n`; в остальных режимах не используется |
| `history_format` | `semantic`: `White Pawn e2-e4`; `numeric`: `White Pawn: (5,2) -> (5,4)` |
| `output_format` | `semantic`: точная строка семантической истории; `numeric`: точная строка числовой истории; `uci`: canonical UCI; `numeric_json`: строгая JSON-схема ниже |

Для `history_mode=full/last_n`: semantic-история требует `output_format=semantic`,
numeric-история — `output_format=numeric`. UCI/JSON доступны при `history_mode=none`.
Даже перед первым ходом, когда история ещё пуста, выбранный формат ответа
остаётся тем же. Это намеренное изменение `classic` относительно старого
UCI-ответа: модель теперь отвечает тем же языком, который видит в истории.

`history_count` считает **полуходы**, не пары White+Black. `last_n=1` явно
помечается `LAST MOVE`; более длинный суффикс — `RECENT MOVES`, не полная игра.
Роли сохраняются: принятый ход человека User, модели Assistant. Даже `none`
сохраняет полную внутреннюю UCI-историю; в модельном запросе её нет.

| Профиль | Состояние | История | Ответ |
| --- | --- | --- | --- |
| `classic` (по умолчанию) | pieces_ascii | full semantic | semantic |
| `classic-last-move` | pieces_ascii | last 1 semantic | semantic |
| `numeric-no-history` | numeric | none | numeric_json |
| `numeric-last-move` | numeric | last 1 numeric | numeric |
| `numeric-short-history` | numeric | last 4 numeric | numeric |
| `numeric-ascii-last-move` | numeric_ascii | last 1 numeric | numeric |
| `hybrid` | numeric_ascii | last 2 semantic | semantic |
| `uci-no-history` | pieces_ascii | none | uci |

Выбор (никакой пересборки):

```sh
cargo run -p bevy-front -- --llm-profile numeric-no-history
cargo run -p llm-match -- --variant Gothic --llm-profile numeric-last-move
LLM_PROFILE=numeric-short-history cargo run -p bevy-front
```

Приоритет: **CLI > переменная процесса LLM_PROFILE > LLM_PROFILE в .env >
active_profile в TOML**. Неизвестный профиль/формат, опечатка поля, нулевой или
отсутствующий `history_count` для `last_n` — явная ошибка. Имя профиля видно в
LLM-меню; действующий профиль и форматы записываются в лог при запуске матча.
`RUST_LOG=llm_match=debug` показывает stripped final answer и декодированный
UCI; reasoning в этих сообщениях отсутствует. В обратную связь попадает только
исходный отклонённый final answer выбранного формата, не его внутренний UCI.

### Координаты, состояние и правила

`x=file+1`, `y=rank`: a1=(1,1), j1=(10,1), a8=(1,8), j8=(10,8).
Terachess II: a1=(1,1), p16=(16,16). При ходе Black оси **не зеркалируются**.
В numeric сохраняется краткая справка a=1, b=2…; сами фигуры, en passant и
маршруты рокировки используют числа. В numeric_ascii буквенная ASCII-доска
добавлена намеренно; semantic-история/ответ в смешанном профиле также
сохраняют буквы. Названия фигур остаются английскими, это не анонимизация.

Состояние содержит размеры, очередь, все фигуры, права рокировки, en passant,
initial king jump Terachess, счётчики полуходов/ходов и число повторений
текущей позиции; Grand также получает начальные количества фигур для
правил восстановления. Нет FEN. Порядок inventory детерминирован: имя,
затем x и y. Геометрические описания принадлежат `engine::PieceKind`, leaper
смещения используют общие с генератором массивы. Giraffe=(2,3)/(3,2).
Движок по-прежнему один решает легальность; описания сложных составных
движений — человекочитаемый текст, а не формальное доказательство правил.

### Формат numeric_json

Используется профилем `numeric-no-history`. В профилях с историей вместо
него ответ имеет точно тот же вид, что запись истории:

```text
White Pawn e2-e4
```

или для числовой истории:

```text
White Pawn: (5,2) -> (5,4)
```

Для взятия нужны соответственно `e4xd5` / `(5,4) x (4,5)`, для промоушена
`=Queen` / ` = Queen`. Для спецходов обязательны те же суффиксы, что в истории:
` (en-passant)`, ` (initial king jump)` либо
` (castling; Rook a1-d1)` / ` (castling; Rook (1,1) -> (4,1))`.
Парсер не только разбирает координаты, но и сравнивает весь final answer с
описанием engine-хода из **предходовой** позиции. Неправильный цвет, имя фигуры,
маркер взятия или аннотация не исправляются. Это не SAN и не извлечение хода
из произвольной строки. При этом человек в CLI всё ещё вводит обычный UCI.

JSON без истории:

```json
{"from":[2,8],"to":[3,6],"promotion":null}
```

Декодируется ровно в `b8c6`, без поиска/исправления хода. Его легальность
зависит от текущей позиции. Промоушен:

```json
{"from":[5,7],"to":[5,8],"promotion":"Queen"}
```

Все три поля обязательны, дополнительные/повторяющиеся поля запрещены.
Координаты — целые, начиная с 1, в пределах доски. Названия промоушена точно
совпадают с легендой (`Queen`, не `queen`); null означает отсутствие
промоушена. Не принимаются markdown, SAN, проза или несколько объектов.
Явное имя фигуры проверяется также после engine-декодирования: одинаковая
UCI-буква не позволяет заменить Archbishop на Amazon. В истории промоушен
сохраняет исходную фигуру: `White Pawn: (5,7) -> (5,8) = Queen`;
взятие использует `x`, спецходы имеют дополнительные аннотации.

### Посмотреть фактический промпт без модели

```sh
cargo run -p llm-match -- --variant Gothic --llm-profile numeric-no-history --print-prompt
cargo run -p llm-match -- --variant Gothic --llm-profile numeric-last-move --moves 'e2e4' --print-prompt
cargo run -p llm-match -- --variant TerachessII --llm-profile numeric-no-history --print-prompt
```

`--moves` принимает каноническую UCI-историю для воспроизводимого примера;
ни HTTP, ни генерация не выполняются. Готовые примеры состояния:
[Gothic numeric-no-history](examples/gothic-numeric-no-history.txt),
[Gothic numeric-last-move](examples/gothic-numeric-last-move.txt),
[Terachess numeric-no-history](examples/terachess-numeric-no-history.txt).

Архитектура: `profile.rs` — схема и выбор; `representation.rs` — состояние,
история и JSON/UCI-парсер; `move_text.rs` — строгая грамматика ответов в формате
истории; `rules.rs` — подстановка в файлы правил;
`Match` — применение ходов и история. Расширение renderer не требует
переписывать логику партии или сеть.

## Проверки

```sh
cargo test -p llm-match
cargo test -p capablanca-engine -p bevy-front --lib --tests
```

Короткие тесты проверяют роли, неизменность позиции/истории после отказов,
строгий UCI, промоушен, двузначные ряды, все варианты и шаблоны. Подставной
HTTP-Kobold проверяет полное/оборванное reasoning, отсутствие final answer,
тихие повторы с неизменным prompt, ошибки HTTP/таймауты и настоящие отказы.
Проверяются семантические взятия/промоушен/спецходы, синхронизация UCI,
геометрия leaper-фигур, отсутствие FEN и утечек legal moves. Реальная модель
для тестов не нужна.

Тесты профилей дополнительно проверяют все клетки досок 10×8/16×16,
абсолютные координаты для Black, filtering none/full/last_n, CLI/env precedence,
строгую JSON-схему, alias-защиту промоушена, точное совпадение semantic/numeric
ответов с историей (включая спецходы), запрет несовместимых настроек и
синхронизацию числового режима с UCI-историей фронтенда.
